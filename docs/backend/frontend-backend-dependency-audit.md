## Invitation lifecycle

Fresh email addresses use `inviteUserByEmail`. An existing Auth identity with no application profile uses a recovery email with a redirect to `/accept-invitation?invitation_id=...`; the Auth UID is retained. A service-role-only helper returns that UID only while the exact invitation is in its provisioning/in-flight state and no matching profile exists. The client establishes the invite or recovery session, verifies the exact invitation UUID and authenticated user, updates the password, verifies the same session again, and calls `accept_user_invitation` with the UUID and entered name. The RPC validates email confirmation and invitation UID/email ownership, then assigns the role/org/district from the invitation and creates the profile transactionally. Enumerator accounts remain inactive until an organization admin approves them with the audited `approve_enumerator_profile(uuid)` RPC. Lost-response retries are idempotent for the same profile/invitation.

Recovery and invite token hashes are accepted only for their respective Auth types and scrubbed from the URL. PKCE callbacks wait for a restored session. The acceptance page only reports success after the RPC returns `pending_approval` or `approved`; pending Enumerators are signed out and shown an approval message. If password update succeeds but acceptance is interrupted, retrying the same invitation uses the existing session and idempotent RPC; it does not create another Auth user, invitation, or profile.
